Rolter emits distributed traces via OpenTelemetry OTLP (gRPC or HTTP), which means you can send spans to any OTel-compatible backend without changing any Rolter code — just set environment variables. Rolter also propagates trace context both inbound (from your clients) and outbound (to upstream engines), so a single trace can span your entire LLM request path from client to model.

<Note>
  Tracing and request logging are independent features. You can use one, both, or neither depending on your observability setup.
</Note>

## Configuration via environment variables

Rolter reads the standard OpenTelemetry SDK environment variables. You don't add anything to `rolter.toml` for tracing — set these in your process environment, systemd unit, Docker Compose file, or Kubernetes deployment:

| Variable | Purpose |
| --- | --- |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | OTLP receiver URL, e.g. `http://otel-collector:4317` for gRPC. **Setting this turns trace export on**; unset keeps tracing stdout-only. |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | `grpc` (default, port 4317) or `http/protobuf` (port 4318) — match your collector's receiver |
| `OTEL_EXPORTER_OTLP_HEADERS` | Authentication headers for managed backends (comma-separated `key=value`) |
| `OTEL_SERVICE_NAME` | Service name that appears on spans in your backend (default `rolter`) — use something like `rolter-gateway` |

<Note>
  Rolter exports **traces** over OTLP. Metrics are exposed on the Prometheus `/metrics` endpoint; point your collector's Prometheus receiver at it (see the topology below) to bring metrics into the same pipeline.
</Note>

## Quick-start examples

<CodeGroup>

```bash Grafana Tempo
export OTEL_EXPORTER_OTLP_ENDPOINT=http://tempo:4317
export OTEL_SERVICE_NAME=rolter-gateway
```

```bash Honeycomb
export OTEL_EXPORTER_OTLP_ENDPOINT=https://api.honeycomb.io
export OTEL_EXPORTER_OTLP_HEADERS="x-honeycomb-team=YOUR_API_KEY"
export OTEL_SERVICE_NAME=rolter-gateway
```

```bash Datadog (via OTLP intake)
export OTEL_EXPORTER_OTLP_ENDPOINT=http://datadog-agent:4317
export OTEL_SERVICE_NAME=rolter-gateway
```

```bash SigNoz
export OTEL_EXPORTER_OTLP_ENDPOINT=http://signoz-otel-collector:4317
export OTEL_SERVICE_NAME=rolter-gateway
```

```bash Langfuse
export OTEL_EXPORTER_OTLP_ENDPOINT=https://cloud.langfuse.com/api/public/otel
export OTEL_EXPORTER_OTLP_HEADERS="Authorization=Basic <base64-encoded-public-secret-key>"
export OTEL_SERVICE_NAME=rolter-gateway
```

## Trace context propagation

Rolter participates in distributed tracing on both sides of the gateway:

<Steps>
  <Step title="Inbound context continuation">
    When a client sends a request with W3C `traceparent` / `tracestate` headers (or `b3` headers), Rolter reads them and continues the existing trace. The gateway span becomes a child of the caller's span — ideal for applications that already instrument their HTTP clients.
  </Step>
  <Step title="Request ID correlation">
    Rolter generates a unique `x-request-id` for every request (or honours a caller-supplied one). This ID is echoed in the response header and stamped on logs, metric exemplars, and spans, giving you a single key to correlate across all three observability signals.
  </Step>
  <Step title="Outbound context injection">
    Rolter injects the active trace context into every upstream request it makes. If your self-hosted engine (vLLM, SGLang, TGI) exports its own spans, they join the same distributed trace automatically — no glue code required.
  </Step>
</Steps>

## Browser tracing for the dashboard

The dashboard can start its own trace in the browser, so a slow screen and the
request behind it are one trace rather than two unrelated stories. It is off by
default.

The dashboard is built ahead of time and served as static assets by the control
plane, so its collector endpoint cannot be baked in at build time. The control
plane injects it into the served HTML instead, as a `window.__ROLTER_CONFIG__`
block. Point it at an **OTLP/HTTP** endpoint:

```bash
ROLTER_UI_OTEL_ENDPOINT=http://localhost:4318/v1/traces \
ROLTER_UI_OTEL_SERVICE_NAME=rolter-ui \
  rolter control
```

<Note>
  This is not `OTEL_EXPORTER_OTLP_ENDPOINT`. That variable configures the
  gateway's own exporter, which speaks gRPC from inside your network. A browser
  needs an OTLP/HTTP endpoint reachable from the **user's** machine, so the two
  are almost never the same URL.
</Note>

With no endpoint set, the dashboard loads no tracing SDK at all — nothing is
downloaded, nothing is exported, and no request headers change. Turning it on
makes the dashboard emit document-load, user-interaction and fetch spans, and
send `traceparent` on its API calls so those spans join the gateway's.

<Warning>
  If you serve the dashboard from a different origin than the control plane, the
  browser will not send `traceparent` cross-origin until that header is allowed
  by CORS, and the dashboard's spans will not join the gateway's. The default
  deployment serves both from the control plane, where this does not arise.
</Warning>

## What's inside a gateway span

Rolter emits one span per pipeline stage, so a slow request is attributable to a
named stage rather than merely slow. A trace of a single chat completion looks
like this:

```text
POST /v1/chat/completions
├─ auth
├─ route.select          strategy, candidates, route
├─ guardrails.pre        redacted, webhook
├─ cache.lookup          hit, kind (exact | semantic)
└─ upstream.request      attempt, gen_ai.system, gen_ai.request.model, status
   ├─ queue.wait         provider
   └─ translate.request
```

`queue.wait` measures only the time the request spent waiting for a provider
worker — not the wait plus the upstream call — so queue pressure is
distinguishable from a slow provider.

Attributes follow the OpenTelemetry [GenAI semantic conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/)
where they fit, so backends with built-in GenAI views light up without extra
configuration.

<Warning>
  Spans never carry prompt or completion content, API keys, virtual-key
  plaintext, or the values of headers you forward upstream. Only structural
  facts — which route, which provider, cache hit or miss, how long — are
  recorded. Redaction stays governed by your existing log settings rather than a
  second policy.
</Warning>

## Metrics over OTLP

The same counters and gauges Rolter serves on `/metrics` are also exported over
OTLP when an endpoint is configured. The Prometheus endpoint is unchanged — this
is a second exporter over the same numbers, so both always agree.

Metrics are collected on the SDK's own interval
(`OTEL_METRIC_EXPORT_INTERVAL`, default 60s) by reading counters the gateway has
already incremented, so exporting them adds nothing to the request path.

## Trying it locally

Rolter ships two opt-in Docker Compose overlays so you can see traces without
signing up for anything:

<CodeGroup>
```bash Jaeger (light, traces only)
docker compose -f docker/docker-compose.yml \
               -f docker/docker-compose.observability.yml up
# traces at http://localhost:16686
```

```bash SigNoz (traces, metrics and logs)
docker compose -f docker/docker-compose.yml \
               -f docker/docker-compose.signoz.yml up
# SigNoz at http://localhost:8080
```
</CodeGroup>

Both wire `OTEL_EXPORTER_OTLP_ENDPOINT` into the gateway and control plane for
you, so bringing one up is the only step. They are mutually exclusive — each
publishes OTLP on 4317/4318.

<Note>
  With no `OTEL_*` environment set, tracing is off and costs nothing: no
  exporter is built, no trace context is parsed beyond what the request log
  already needed, and the request path is unchanged.
</Note>

## Recommended topology

For production setups, deploy an OpenTelemetry Collector as an intermediary between Rolter and your backends. This decouples your gateway from vendor specifics and lets you fan out to multiple backends or change destinations without restarting Rolter.

```text
Rolter gateway
    │
    │  OTLP (gRPC/HTTP)
    ▼
OpenTelemetry Collector
    │           │           │
    ▼           ▼           ▼
  Grafana    Honeycomb   Datadog
  Tempo
```

The Collector can also scrape Rolter's `/metrics` endpoint and your upstream engines' `/metrics` endpoints in the same deployment, keeping all telemetry paths consistent.

## End-to-end traces with vLLM

<Tip>
  If you run vLLM with `--otlp-traces-endpoint` pointing at the same OpenTelemetry Collector as Rolter, engine-level prefill and decode spans will appear as children of Rolter's gateway span in the same distributed trace. You get a complete picture — from the client request, through gateway routing, down to individual inference steps — in a single trace view.
</Tip>

```bash vLLM launch with tracing
python -m vllm.entrypoints.openai.api_server \
  --model meta-llama/Llama-3.1-8B-Instruct \
  --otlp-traces-endpoint http://otel-collector:4317
```

Point `OTEL_EXPORTER_OTLP_ENDPOINT` for Rolter at the same collector and the spans join automatically via the injected `traceparent` header.

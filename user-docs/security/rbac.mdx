Rolter's role-based access control (RBAC) system governs what each human user can do in the control plane — creating routes, managing virtual keys, adjusting budgets, and reading dashboards. Roles are lightweight and composable: you assign them per scope, so a user can hold different permissions in different parts of your organisation.

## Roles

Rolter ships with three built-in roles. Every role applies within the scope it is granted — it does not automatically extend to parent or sibling scopes.

<CardGroup cols={3}>
  <Card title="admin" icon="shield-check">
    Full control within the assigned scope. Admins can manage providers, routes, virtual keys, members, and budgets. Use this role sparingly — at most for a small platform team.
  </Card>

  <Card title="member" icon="pencil">
    Create and edit routes and virtual keys within their scope. Members cannot change org-level settings or manage other users' memberships.
  </Card>

  <Card title="viewer" icon="eye">
    Read-only access to dashboards, request logs, and usage data. Assign this role to stakeholders who need visibility without the ability to make changes.
  </Card>
</CardGroup>

## Scopes

Roles are always granted at a specific scope. Rolter organises resources in a four-level hierarchy:

<Steps>
  <Step title="Org">
    The top-level container for all your teams, projects, and virtual keys. An org-level admin can manage everything beneath it.
  </Step>
  <Step title="Team">
    A named group within an org — typically a product team or business unit. Teams own one or more projects.
  </Step>
  <Step title="Project">
    The primary unit of work. Routes, virtual keys, and budgets are attached to projects. Most day-to-day administration happens at this level.
  </Step>
  <Step title="Virtual Key">
    Individual API credentials. Budgets and rate limits can be scoped to a single key for fine-grained per-client control.
  </Step>
</Steps>

## Assigning roles per scope

A user can hold a different role at each scope level. For example, a developer might be a **member** in their team's project but only a **viewer** in the shared infrastructure project. Permission checks resolve the most specific membership for the resource being accessed.

```text
Alice  →  admin   at  org: acme
Bob    →  member  at  project: payments-api
Carol  →  viewer  at  team: platform
```

<Note>
  The control plane enforces RBAC for all management operations. The gateway data plane does not consult roles — it checks that the incoming virtual key exists, is active, and is allowed to access the requested model. The one place the two meet is an access profile's [model and route policy](#model-and-route-policy), which does reach the gateway.
</Note>

## Ask the server what a role can do

Rolter publishes its own permission table, so you never have to keep a copy in sync with the deployment:

| Endpoint | Answers |
| --- | --- |
| `GET /api/v1/rbac/matrix` | For every resource, the minimum role each of read / create / update / delete takes — or that the action is reserved for a superadmin, open to any authenticated caller (`authenticated_only`), or does not exist. |
| `GET /api/v1/rbac/effective?org_id=&team_id=&project_id=` | What *you* may do at that scope, resolved from your own memberships. |

Both read the same table the control plane enforces with, so the answer is never a guess: a request that `effective` says you cannot make returns `403` if you make it anyway.

<Note>
  Deployment-wide settings — feature flags, runtime, logging, compatibility and adaptive-routing policy, cluster nodes, security settings, alerting and the model pricing catalog — sit outside the org/team/project hierarchy. No org role reaches them; they require the deployment admin token or a superadmin account. The same is true of editing or deleting a user account, which spans every org that user belongs to.
</Note>

## Custom roles and access profiles

The three built-in roles are a floor, not the limit. An organization can define its own **custom roles**: pick a base role, then add the exact `resource:action` pairs it should also allow.

```bash
curl -X POST https://control.example.com/api/v1/orgs/$ORG_ID/custom-roles \
  -H "Authorization: Bearer $ROLTER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
        "name": "Provider Wrangler",
        "base_role": "member",
        "grants": [{"resource": "provider", "action": "create"}]
      }'
```

A grant can only **widen**. A custom role never removes what its base role already allowed, so existing admin/member/viewer behaviour is untouched and nothing needs migrating.

Custom roles are not handed to people one at a time. You compose them into an **access profile**, which pairs each role with the org, team or project it applies at, and assign that profile to users or teams:

```bash
# "auditor across the org, and deploy admin on one project"
curl -X POST https://control.example.com/api/v1/orgs/$ORG_ID/access-profiles \
  -H "Authorization: Bearer $ROLTER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
        "name": "Platform On-Call",
        "roles": [
          {"role_id": "'$AUDITOR_ROLE'",  "org_id": "'$ORG_ID'"},
          {"role_id": "'$DEPLOY_ROLE'", "project_id": "'$PROJECT_ID'"}
        ]
      }'

curl -X POST https://control.example.com/api/v1/access-profiles/$PROFILE_ID/assignments \
  -H "Authorization: Bearer $ROLTER_TOKEN" \
  -d '{"user_id": "'$USER_ID'"}'
```

Scope is honoured exactly as it is for memberships: a grant attached to one project authorizes that project, not the whole org.

## Model and route policy

A profile can also carry a **model and route policy** — allow and deny lists for the models and routes its holders may reach. Entries are exact names or a trailing-`*` prefix glob (`gpt-*`), an empty allow-list means "no restriction", and deny always wins over allow. Where someone holds several profiles the lists are unioned, never intersected, so giving a person another profile can only ever widen their access.

It is reported on `GET /api/v1/rbac/effective` as `model_policy`, and the gateway enforces it. Because a policy belongs to a person while a request carries a key, rolter resolves the policy of each virtual key's **creator** and attaches it to that key. A denied model returns `403` with code `model_not_allowed`; a denied route returns `403` with code `route_not_allowed`.

<Note>
  A key's own model list and its creator's policy are both applied, and neither widens the other. A key that names `gpt-4o` still cannot reach it if its creator's profile denies it — and a profile that allows `gpt-4o` does not add it to a key scoped to something else.

  Keys with no creator — those made by an admin on someone's behalf, or defined in the config file — carry no policy at all, since there is no person whose profiles could apply. Restrict those with the key's own model list.
</Note>

Policy changes propagate to the gateway the same way provider and route changes do, on the next config refresh rather than instantly. Assigning or revoking a profile, editing its policy, and adding or removing someone from a team all trigger that refresh.

<Warning>
  Deleting a custom role that a profile still references returns `409` rather than quietly emptying that profile — detach it first. Deleting a *profile* does remove its assignments, since they mean nothing without it. Every change to a role, profile, assignment or policy is written to the audit log with its before and after, because all of them change what real people can do.
</Warning>

`GET /api/v1/rbac/matrix?org_id=` returns your org's custom roles alongside the built-in ones, so the dashboard's matrix always reflects the current rule set.

## Open mode: running with no admin token

If `ROLTER_ADMIN_TOKEN` is not set, the control plane has **no authentication at
all**: every request to the management API (`/api/v1/*`) and to
`/internal/snapshot` is served as superadmin. Anyone who can reach the port can
read and rotate keys and change providers, routing and budgets.

This exists as a zero-credential local-development affordance, and Rolter keeps
it from becoming anything else:

- **It cannot bind a public interface by accident.** With no admin token set,
  the control plane refuses to start unless every listener — the API port and
  `--internal-addr`, when split out — is on loopback. Binding `0.0.0.0` in this
  state exits with an error naming the variable that closes it.
- **It is loud.** Every start in open mode logs a warning naming what is
  unprotected, rather than only that a variable is missing.
- **It is visible.** The dashboard shows a persistent banner for as long as the
  control plane it is talking to is unauthenticated.

Set the token to close it:

```bash
export ROLTER_ADMIN_TOKEN="$(openssl rand -hex 24)"
```

<Warning>
  `--allow-open-mode` (`ROLTER_ALLOW_OPEN_MODE=1`) overrides the loopback
  refusal and serves an unauthenticated control plane on whatever interface you
  bound. There is no scenario in which that is right for a deployment reachable
  by anyone else — the flag exists so that a container or CI harness that must
  bind `0.0.0.0` can do so deliberately, on a network you control.
</Warning>

## Most-restrictive-wins

When evaluating budgets and rate limits, Rolter walks the scope chain from org down to the individual key and applies the most restrictive matching rule. This means an org-level budget acts as a hard ceiling even if a project-level budget is more generous — and a per-key rate limit can tighten throughput below what the project allows.

<Tip>
  Use this to your advantage: set a broad org-level budget as a safety net, then add project- or key-level limits to give individual teams or clients their own allocation. See [Budgets & Rate Limits](/security/budgets-and-rate-limits) for configuration details.
</Tip>

## User accounts

Rolter v1 ships with **local user accounts** secured with username and password. You create and manage accounts through the control plane dashboard or API.

**OAuth2 / OIDC SSO** — with group-to-role mapping for identity providers such as Okta, Auth0, and Google Workspace — is on the roadmap and will be available in a future release.

<Info>
  If your organisation requires LDAP or SAML-based authentication, reach out to discuss the enterprise roadmap.
</Info>
